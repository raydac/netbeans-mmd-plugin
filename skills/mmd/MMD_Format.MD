# MMD format

MMD is a UTF-8 plain-text mind map format used by Scia Reto, the NetBeans plugin, and the IntelliJ IDEA plugin. The file is Markdown-compatible on purpose: a `.mmd` file can be opened in a text editor and still reads as a document.

This specification is part of the `mmd` agent skill. Copying the skill folder includes this file together with the parse/write/validate/crypto scripts.

Canonical current format version written by the model is **`1.1`** (`MindMap.FORMAT_VERSION`). The parser always stores `__version__` as `1.1` after a successful load, even if the file contained another value.

This description matches the `mind-map-model` lexer (`MindMapLexer`), map parser (`MindMap`), topic parser (`Topic.parse`), extras, and their unit tests. Encrypted-note **ciphertext** is produced outside the model, by Swing `CryptoUtils`; the algorithm is specified under [encrypted notes](#encrypted-notes).

## 1. File anatomy

A file has two parts, separated by a header delimiter line:

```
<header lines>
---
<body: topics, extras, snippets>
```

```
[Scia Reto](https://sciareto.org) mind map
> __version__=`1.1`
---

# Root
```

The writer emits a Markdown hard line-break after the title (three spaces, then `\n`), then one attribute line, then `---`:

```
[Scia Reto](https://sciareto.org) mind map<SP><SP><SP>
> __version__=`1.1`
---
```

Older files may start with a free-form comment such as `Mind Map generated by NB MindMap plugin`. The parser does not require a specific header title.

Line endings in the written form are always `\n`. The lexer treats `\n` as the line terminator. `\r` is kept inside extra `<pre>` bodies (notes can contain mixed `\r\n` and `\n`).

## 2. Header

The lexer starts in `HEAD_LINE` state and reads line by line until it sees a **header delimiter**.

### 2.1 Header delimiter

A delimiter is a whole line that contains only the character `-` (at least one), optionally ending with `\n`. `\r` on that line is ignored.

| Line | Meaning |
|------|---------|
| `--` | delimiter |
| `---` | delimiter (canonical write form) |
| `---------------` | delimiter |
| `-- ` (trailing space) | **not** a delimiter — still a header line |

Without a delimiter the parse fails with `IllegalArgumentException` (“end of header is not found”). Empty input and a lone comment with no `-` line both fail that way.

A delimiter with no following topic yields an empty map (`root == null`). That is valid.

### 2.2 Map attributes

A header line that starts with `> ` (greater-than, space) is a map attribute line. Several such lines are allowed; later keys override earlier ones. Blank lines between attributes and the delimiter are ignored.

```
Some title
> __version__=`1.1`,showJumps=`true`
> generatorId=`com.example:tool:1.0`
---
```

Attribute syntax is described in [section 6](#6-attributes).

### 2.3 Standard map attributes

| Name | Required | Meaning |
|------|----------|---------|
| `__version__` | written always | Format version. Writer always writes `1.1`. |
| `showJumps` | optional | `"true"` to draw jump arrows for internal topic links. |
| `generatorId` | optional | Identifier of the application that produced the file. |
| `noBaseFolder` | optional | File links were stored without a project base folder; resolve them relative to the `.mmd` file’s directory. |

Unknown map attributes are kept as-is.

## 3. Topics

After the delimiter, the body is a tree of ATX-style headings. Level is the number of leading `#` characters.

```
---

# Root

## Child A

### Grandchild

## Child B
```

This is the tree:

```
Root
├── Child A
│   └── Grandchild
└── Child B
```

### 3.1 Heading line

```
#{level}[separator]{title}\n
```

- `level` is one or more `#`.
- If the next character is whitespace other than `\n`, **one** whitespace character is consumed as separator and is not part of the title. Remaining spaces stay in the title.
- If the next character is not whitespace (`#Topic`), the whole remainder is the title.
- `#` alone followed by end of file does **not** create a topic (no title token).
- `#` followed by only spaces does create a topic whose text is those remaining spaces.

Examples:

```
# Root          → text "Root"
#Topic          → text "Topic"
#               → no topic if nothing follows
# \n            → empty title
#         \n    → title of remaining spaces
```

Leading spaces before `#` are skipped. This is valid:

```
   # Topic
```

### 3.2 Title encoding

On write, the title is Markdown-escaped. On read, ISO control characters are stripped, then Markdown is unescaped.

**Newlines in a title** are stored as HTML breaks (case-insensitive):

| Written | Parsed title |
|---------|----------------|
| `Hello<br/>World` | `Hello\nWorld` |
| `Hello<br>World` | `Hello\nWorld` |
| `Hello<br />World` | `Hello\nWorld` |

**Characters escaped with a backslash** on write:

```
\ ` * _ { } [ ] ( ) # < > + - . !
```

ISO control characters other than `\n` are dropped on write.

```
# \<Level1\><br/>NextText
```

parses as title `<Level1>\nNextText`.

A title that starts with `#` must be escaped, otherwise it would look like a deeper heading on a later round-trip of the heading marker itself. The model writes:

```
## \#NewTopic
```

which parses back as `#NewTopic`.

A literal dot in the middle of a title is escaped because `.` is in the Markdown special set:

```
## Level2\.1
```

parses as `Level2.1`.

### 3.3 Hierarchy rules

The parser keeps a current topic and a current depth (number of `#` of that topic).

| Incoming `#` count | Action |
|--------------------|--------|
| `depth + 1` | Child of the current topic |
| `depth` | Sibling (same parent) |
| `< depth` | Walk up `depth - newLevel` parents, then add a sibling there |
| `> depth + 1` | Still attached as a child of the **current** topic; current depth jumps to the new level |

The first topic must be level 1 (`#`). A file that starts with `##` creates no root.

Skipped levels are accepted. This file:

```
# Root
#### Deep
## Sibling
```

attaches `Deep` under `Root` (even though `####` is not `##`), then `Sibling` is a child of `Root` after walking back up.

Children are kept in document order.

### 3.4 Empty and missing root

```
---
```

is a valid empty map.

```
---
#
```

has no root (heading never completed).

## 4. Topic extras

A topic may carry at most one extra of each type: `FILE`, `LINK`, `NOTE`, `TOPIC`. The type name is the Java enum name and is case-sensitive.

Written form:

```
- TYPE
<pre>…payload…</pre>
```

The type line must be `-` followed by a space, then the type name, then the rest of the line (trailing spaces are allowed). The payload must be a `<pre>…</pre>` block; a different tag is treated as an unknown line and the extra is dropped.

The type line and the `<pre>` block belong to the **current** topic. An unknown line between them cancels the pending type.

On write, extras are emitted in alphabetical type order: `FILE`, `LINK`, `NOTE`, `TOPIC`. Attributes (if any) are written **before** extras.

HTML specials inside `<pre>` are escaped on write and unescaped on read (HTML 3 entities):

| Char | Written |
|------|---------|
| `"` | `&quot;` |
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |

Invalid extra payloads: if the map is loaded with `ignoreErrors=true` (the default `MindMap(Reader)` constructor), the extra is skipped. With `ignoreErrors=false`, parse throws.

An unknown type name (`- FOO`) is ignored.

### 4.1 `NOTE` — text note

Payload is the note text, newlines preserved, HTML unescaped.

```
# Topic
- NOTE
<pre>Some
text</pre>
```

A note may contain backticks and HTML; they are escaped in the `<pre>` body, not treated as Markdown:

```
# \`Root<br/>topic\`
- NOTE
<pre>Hello world
 &lt;br&gt;```Some```</pre>
```

parses as title `` `Root\ntopic` `` and note `Hello world \n <br>```Some``` `.

#### Encrypted notes

`mind-map-model` does **not** encrypt or decrypt. It stores an opaque `NOTE` payload plus two topic attributes. Scia Reto, the NetBeans plugin, and the IntelliJ plugin encrypt and decrypt that payload with `com.igormaznitsa.mindmap.swing.panel.utils.CryptoUtils` (`CryptoUtilsTest` is the interoperability vector). The password is never written to the file.

```
# Secret
> extras.note.encrypted=`true`,extras.note.encrypted.hint=`tip`

- NOTE
<pre>gJLc5oWXTyeLeu24WhyqdlDFoGMgvuTvTzOx4hdCRx8JYjXMUoziQFR+fyiO3/rtRiiy2BVXTM04CUbp8dkb5A==</pre>
```

| Attribute | Required when encrypted | Meaning |
|-----------|-------------------------|---------|
| `extras.note.encrypted` | yes | Ciphertext flag. Parsed with `Boolean.parseBoolean` (true only for `"true"` ignoring case). Missing, empty, or any other string means **not** encrypted. Writer emits `true`. |
| `extras.note.encrypted.hint` | no | Password **hint** in clear text. Not a secret. Omitted when there is no hint. |

On write, `ExtraNote` emits `extras.note.encrypted=`true`` when `isEncrypted()` is true, and emits the hint when it is non-null. On attach to a topic, a non-encrypted note **removes** both attributes.

The `<pre>` body is the ciphertext string (Base64). It is HTML-unescaped like any other note (`Extra.ExtraType.parseLoaded`); the Base64 alphabet `A–Z a–z 0–9 + / =` is unchanged by that unescape. The body is **not** trimmed; `\r\n` is kept.

Encrypted notes are not exported (`ExtraNote.isExportable()` is false) and are not matched by content search (`containsPattern` skips encrypted notes).

##### Password

- The password is only in memory while the editor (or a compatible tool) encrypts or decrypts.
- Editors take it from `PasswordPanel` and **trim** surrounding whitespace (`String.trim()`) before `CryptoUtils`.
- `AbstractNoteEditorData.isEncrypted()` is true only when the password is non-null and not empty after trim. An empty password therefore does not set `extras.note.encrypted`.
- `CryptoUtils.encrypt` with a null or empty password returns the plaintext **unchanged** (no AES). Callers that still mark the note encrypted would store readable text under the encrypted flag; the UI does not do that.

##### Cipher

`Cipher.getInstance("AES")` with a 32-byte `SecretKeySpec` is **AES-256 / ECB / PKCS5Padding** (PKCS #7 padding on 16-byte blocks). There is **no IV and no salt**. Key and integrity check both use SHA-256.

| Piece | Value |
|-------|--------|
| Character encoding | UTF-8 (`StandardCharsets.UTF_8`) |
| Key | `SHA-256(UTF-8 password)` — 32 bytes = AES-256 |
| Integrity prefix | `SHA-256(UTF-8 plaintext)` — 32 bytes, prepended **before** AES |
| Payload | `SHA-256(plaintext) \|\| UTF-8 plaintext` |
| Cipher | AES-256-ECB, PKCS5/PKCS7 padding |
| File encoding | `java.util.Base64` basic encoder / decoder (`Utils.base64encode` / `base64decode`), no line wrapping |

##### Encrypt (`CryptoUtils.encrypt`)

1. If the password is null or empty, return the plaintext as-is.
2. `textBytes = UTF-8(plaintext)`.
3. `payload = SHA-256(textBytes) || textBytes`.
4. `key = SHA-256(UTF-8(password))`.
5. AES-256-ECB-PKCS5 encrypt `payload` with `key`.
6. If the ciphertext bytes equal `payload`, throw (`IllegalStateException`) — the provider did not encrypt.
7. Return Base64 of the ciphertext (ASCII, with `=` padding as needed).

##### Decrypt (`CryptoUtils.decrypt`)

1. `key = SHA-256(UTF-8(password))`.
2. Base64-decode the `<pre>` body.
3. AES-256-ECB-PKCS5 decrypt.
4. If the result is shorter than 32 bytes, fail (return `false`).
5. Split into `storedHash = bytes[0..32)` and `textPart = bytes[32..]`.
6. If `SHA-256(textPart)` is not equal to `storedHash`, fail (wrong password or corrupt data).
7. Append `UTF-8(textPart)` to the output buffer and return `true`.

| Failure | Result |
|---------|--------|
| Wrong password (bad PKCS5 padding) | `false` (`BadPaddingException`) |
| Wrong password (padding luckily valid, hash mismatch) | `false` |
| Empty ciphertext | `false` (too short after decrypt, or empty input) |
| Invalid Base64 | `IllegalArgumentException` from the decoder (not treated as a wrong password) |
| Other JCA errors (`IllegalBlockSizeException`, missing AES) | `RuntimeException` |

Editors show an error dialog on `false` (“wrong password”) or on `RuntimeException` (“can’t decode”). They do not replace the stored ciphertext with guessed plaintext.

##### Interoperability vector (`CryptoUtilsTest`)

| Field | Value |
|-------|--------|
| Password | `hello` |
| Plaintext | `Hello Crypto-World` |
| Ciphertext (Base64) | `gJLc5oWXTyeLeu24WhyqdlDFoGMgvuTvTzOx4hdCRx8JYjXMUoziQFR+fyiO3/rtRiiy2BVXTM04CUbp8dkb5A==` |

Wrong passwords `hello1` and `""` must fail. That string is also the payload in the example topic above.

##### Layout of the AES input

```
+----------------------+---------------------------+-----+
| SHA-256(plaintext)   | UTF-8 plaintext           | pad |
| 32 bytes             | N bytes                   | 1–16|
+----------------------+---------------------------+-----+
        \________________ AES-256-ECB-PKCS5 _____________/
                          then Base64
```

PKCS5 padding is always present (a full 16-byte block of `0x10` when `32 + N` is already a multiple of 16).

### 4.2 `LINK` — URI

Payload is a URI (trimmed). It must be accepted by `URI.create`; otherwise the extra is invalid.

```
# Topic
- LINK
<pre>http://www.google.com</pre>
```

Surrounding spaces inside `<pre>` are trimmed:

```
<pre>  http://www.google.com </pre>
```

Fragment-only values such as `#82b1f2` are accepted as URIs.

On write, the URI is stored with query parameters included (`MMapURI.asString(false, true)`).

### 4.3 `FILE` — file link

Same wrapping as `LINK`, but the value is a file URI or a relative path. The scheme may be omitted; a missing scheme or `file:` is treated as a file link.

```
# Topic
- FILE
<pre>./notes.txt</pre>
```

```
- FILE
<pre>file:///item1/item2/item2.txt</pre>
```

Query parameters on file links are kept separately from the path. A common pattern is a source line:

```
- FILE
<pre>src/main/java/Example.java?line=42</pre>
```

Relative paths are resolved against the mind map base folder (or, if `noBaseFolder` is set, the `.mmd` file directory). Absolute `file:` URIs are used as-is.

A `.mmd` target is flagged in the model as another mind map (`ExtraFile.isMMDFile()`), but that is not a separate syntax — it is inferred from the extension.

### 4.4 `TOPIC` — jump to another topic

Payload is the target topic’s `topicLinkUID` attribute (trimmed). The target topic must carry that attribute.

```
# Root
> topicLinkUID=`14F9D4CD31DA`

## Other
- TOPIC
<pre>14F9D4CD31DA</pre>
```

UI-generated UIDs are hex-like (`14F9D4CD31DA`, `1553A050A42A`). Any non-empty string is accepted. The writer of `ExtraTopic.makeLinkTo` assigns a unique hex timestamp plus a letter if the target has no UID yet.

`showJumps=`true`` on the map asks the editor to draw these jumps.

## 5. Code snippets

A topic may hold one snippet per language name. Syntax is a Markdown fenced block attached to the **current** topic. The examples use a four-backtick wrapper so GitHub leaves the inner MMD fences intact.

````text
# Root
```Java
System.exit(0);
```
```Shell
exit
```
````

The opening fence is a line that starts with <code>&#96;&#96;&#96;</code> and is **not** made only of backticks. The rest of that line (after the three backticks), trimmed, is the language key, for example <code>&#96;&#96;&#96;Java</code>.

The closing fence is a line that is exactly three backticks at column 0 (optional trailing `\n`). These are **not** closers and stay in the body:

| Line | Role |
|------|------|
| <code>&#96;&#96;&#96;</code> | closer |
| <code>&#96;&#96;&#96;&#96;</code> or more | body |
| <code>&#96;&#96;&#96;a</code> | body |
| <code>a&#96;&#96;&#96;</code> | body |
| leading space before <code>&#96;&#96;&#96;</code> | body |
| <code>&#96;&#96;&#96;</code> then space then a backtick | body |

An empty snippet is stored as `""`:

````text
```Java
```
````

An unclosed snippet is **not** stored.

On write, languages are sorted, a trailing `\n` is added to the body if missing, and the block is:

````text
```{language}
{body}
```
````

Several snippets on one topic are allowed. The same language key overwrites the previous snippet.

## 6. Attributes

Attribute lines appear in the header (map) or immediately under a topic (topic). Form:

```
> name=`value`,other=`value2`
```

Rules:

- The line must match `^\s*>\s(.+)$` — `>` then a space, then the list.
- Each pair is `name = fence value fence`.
- `name` is a run of non-whitespace characters.
- `value` is wrapped in one or more backticks. The fence is the longest run of backticks that does **not** occur in the value, plus one (on write).
- Pairs are separated by commas. Extra spaces around `=` and after commas are allowed.
- Keys are case-sensitive. Duplicate keys: last value wins.
- On write, keys are sorted lexicographically.

Backticks inside a value:

```
> hello=``wor`ld``
```

parses as `hello` → `wor`ld`.

A value that is only spaces or empty is legal (`name=`` ` `` with appropriate fences). The writer uses at least one backtick.

### 6.1 Standard topic attributes

| Name | Typical value | Meaning |
|------|---------------|---------|
| `fillColor` | `#7AA3E5` | Background fill (HTML hex). |
| `textColor` | `#000000` | Title color. |
| `borderColor` | `#FF0000` | Border color. |
| `leftSide` | `true` | Place this topic on the left of the root. Only first-level children. |
| `collapsed` | `true` | Hide children. |
| `topicLinkUID` | `14F9D4CD31DA` | Anchor for `TOPIC` extras. |
| `mmd.emoticon` | `acorn` | Emoticon id. See [Appendix A](#appendix-a-embedded-emoticon-ids). |
| `align` | `left`, `center`, `right` | Title alignment. |
| `mmd.image` | Base64 | Embedded image bytes. |
| `mmd.image.name` | file name | Image name. |
| `mmd.image.uri` | URI | Image URI. |
| `extras.note.encrypted` | `true` | See [encrypted notes](#encrypted-notes). |
| `extras.note.encrypted.hint` | text | Clear-text password hint. Never the password. |

Custom attributes are allowed and round-trip.

Boolean flags are stored as the string `true`. Missing means false.

Colors in existing maps are `#` plus 6 hex digits.

### 6.2 Write order under a topic

1. Heading line.
2. If the topic has attributes or extras that contribute attributes: one `> …` line, then a blank line.
3. Extras, each type then `<pre>`, then a blank line after each extra.
4. Code snippets, sorted by language.
5. Child topics, each starting with a blank line before its heading.

````text
# Level1
> hello=``wor`ld``

- LINK
<pre>http://wwww.igormaznitsa.com</pre>
```Java
System.exit();
```
```Shell
exit
```

## Child
````

## 7. Canonical written file

`MindMap.write` always produces this skeleton:

```
[Scia Reto](https://sciareto.org) mind map
> __version__=`1.1`[,sorted other map attributes]
---
<optional root topic tree>
```

The three spaces before the first newline are a Markdown line break (`NEXT_PARAGRAPH`). Map attributes always include `__version__=`1.1`` and are sorted by name.

A map with no root:

```
[Scia Reto](https://sciareto.org) mind map
> __version__=`1.1`
---
```

A map with a root and one attribute:

```
[Scia Reto](https://sciareto.org) mind map
> __version__=`1.1`,hello=`World`
---

# Root
```

````text
[Scia Reto](https://sciareto.org) mind map
> __version__=`1.1`,generatorId=`com.igormaznitsa:mind-map-annotation-processor:1.7.0`,showJumps=`true`
---

# Root topic
> borderColor=`#FF0000`,fillColor=`#00FFFF`,mmd.emoticon=`acorn`,textColor=`#FFA500`,topicLinkUID=`rootTopicUid`

- FILE
<pre>src/Root.java?line=10</pre>
- LINK
<pre>https://sciareto.com</pre>
- NOTE
<pre>Some test
multiline note
one more line</pre>

## Left child
> leftSide=`true`,mmd.emoticon=`abacus`

- FILE
<pre>src/Root.java?line=24</pre>

### Jump back
- TOPIC
<pre>rootTopicUid</pre>
```Java

```
````

Tree:

```
Root topic          [colors, emoticon, UID, file, link, note]
├── Left child      [left side, emoticon, file]
│   └── Jump back   [internal jump to Root, Java snippet]
```

## 9. Lexer tokens

`MindMapLexer` is a line-oriented lexer used both for `MindMap`/`Topic.parse` and for IDE PSI parsing. It can resume mid-token when the buffer grows (incomplete header delimiter, attribute, extra `<pre>`, or topic title).

| Token | When |
|-------|------|
| `HEAD_LINE` | Header text line (not `> ` and not a delimiter). |
| `HEAD_DELIMITER` | Line of only `-`. |
| `ATTRIBUTE` | Line starting with `> ` (also a header `HEAD_LINE` reclassified if it starts with `> `). |
| `WHITESPACE` | Whitespace / ISO control between body tokens. |
| `TOPIC_LEVEL` | The `#` run and optional following space. |
| `TOPIC_TITLE` | Remainder of the heading line. |
| `EXTRA_TYPE` | `- TYPE…` line. |
| `EXTRA_TEXT` | `<pre>…</pre>` (must start with `<pre>`). |
| `CODE_SNIPPET_START` | Opening <code>&#96;&#96;&#96;lang</code> line. |
| `CODE_SNIPPET_BODY` | Text until a valid closer. |
| `CODE_SNIPPET_END` | Closer <code>&#96;&#96;&#96;</code>. |
| `UNKNOWN_LINE` | Anything else (ignored by the topic parser, except that it cancels a pending extra type). |

Tokens are contiguous: each token’s start equals the previous token’s end. The lexer test `cancer_risk.mmd` concatenates every token and must reproduce the file exactly.

A line that is not a heading, attribute, extra, snippet fence, or whitespace is `UNKNOWN_LINE` and is ignored. Trailing garbage after the tree is therefore harmless.

## 10. Parser behaviour and edge cases

These behaviours are covered by `MindMapTest`, `TopicTest`, `MindMapLexerTest`, and `ModelUtilsTest`.

| Input / situation | Result |
|-------------------|--------|
| Empty file | `IllegalArgumentException` |
| Text without a `-` delimiter line | `IllegalArgumentException` |
| Header + delimiter, no topics | `root == null` |
| Several `> key=`…`` lines | last value wins |
| Blank lines after delimiter before `#` | ignored |
| First heading not `#` | no root |
| Unclosed `` ``` `` | snippet not stored |
| `<pra>…</pre>` | not an extra (`UNKNOWN_LINE`) |
| Spaces inside LINK `<pre>` | trimmed, URI must still parse |
| NOTE body | not trimmed; `\r\n` kept |
| `extras.note.encrypted=`true`` | `<pre>` is Base64 ciphertext; model does not decrypt |
| Default `new MindMap(reader)` | `ignoreErrors=true` |
| `new MindMap(reader, false)` | invalid extras throw |
| After load | `__version__` forced to `1.1` |
| Round-trip of special titles | escape/unescape is stable for the Markdown special set and `<br/>` |

Markdown unescape also turns `\<br>`-style escaped specials back into the literal character (`\\` → `\`, `\`` → `` ` ``, and so on).

Attribute fences use a non-greedy match `(\`+)(.*?)` + same fence, so the first matching closer ends the value.

## 11. URI notes (`MMapURI`)

`LINK` and `FILE` extras store an `MMapURI`:

- Non-file schemes (`http`, `https`, …) keep the full URI, including query and fragment, as a single URI.
- File URIs (`file:` or no scheme) split `?` query parameters into a property map. The path is the URI without the query. On write, parameters are appended again as `key=value` pairs, keys sorted, values `application/x-www-form-urlencoded`.
- Relative file paths are resolved against the mind map base folder when converting to `File`.
- Spaces in `file:` paths may appear raw or as `%20`; both are accepted when building a `File`.

## 12. Minimal recipes

**Empty map with root**

```
[Scia Reto](https://sciareto.org) mind map
> __version__=`1.1`
---

# 
```

(The writer always inserts a space after the `#` run, then the escaped title. An empty title is therefore `# ` plus newline, after a leading blank line.)

**Two levels, no extras**

```
---
# Solar
## Earth
### Moon
```

Header may be any text plus `---`. The writer always adds the Scia Reto title and `__version__`.

**Internal link**

```
# A
> topicLinkUID=`A1`

## B
- TOPIC
<pre>A1</pre>
```

**Note + URL + file**

```
# Task
- FILE
<pre>./spec.pdf</pre>
- LINK
<pre>https://example.com</pre>
- NOTE
<pre>Read the spec first.</pre>
```

**Encrypted note** (password `hello` → plaintext `Hello Crypto-World`; see [encrypted notes](#encrypted-notes)):

```
# Secret
> extras.note.encrypted=`true`,extras.note.encrypted.hint=`tip`

- NOTE
<pre>gJLc5oWXTyeLeu24WhyqdlDFoGMgvuTvTzOx4hdCRx8JYjXMUoziQFR+fyiO3/rtRiiy2BVXTM04CUbp8dkb5A==</pre>
```

## Appendix A. Embedded emoticon IDs

Topic attribute `mmd.emoticon` stores the id of an icon shipped with **mind-map-swing-panel**.
The panel loads the catalog from `MiscIcons` (`/com/igormaznitsa/mindmap/swing/miscicons/icon.lst`)
and the PNG `…/miscicons/{id}.png`.

```
# Topic
> mmd.emoticon=`acorn`
```

Rules:

- Ids are **case-sensitive** and match the file stem of the PNG (lowercase with underscores).
- The catalog below has **407** ids (the `icon.lst` order).
- Selecting **empty** in the emoticon dialog **removes** the attribute; `empty` is a blank 32×32 placeholder used by the chooser, not a value normally written to `.mmd`.
- An unknown id is kept in the file but is not drawn (`MiscIcons.findForName` returns null).
